# Secrets

Le panneau **Secrets** (barre latérale) gère les identifiants dont vos workflows ont
besoin — token z/OSMF, clé SSH, mot de passe SMTP, clé d'API LLM. Il fonctionne **en
écriture seule**, adossé au **trousseau de l'OS** (sous-titre « write-only · OS keychain ») :
une valeur saisie est chiffrée par le système d'exploitation, puis **jamais** renvoyée à
l'interface ni journalisée.

Les secrets sont **globaux** : contrairement aux workflows et aux exécutions, ils ne sont
**pas** cloisonnés par espace de travail. Un identifiant est généralement commun aux projets
d'un même utilisateur — voir [Espaces de travail](./espaces).

:::info Écriture seule, par principe
Le serveur n'expose **aucun** endpoint capable de relire une valeur. `GET` ne renvoie que
des **noms** et des **métadonnées non secrètes** (type, rotation, expiration, date de mise à
jour). La valeur ne circule qu'une fois, du navigateur vers le trousseau, dans le **corps**
d'une requête — jamais dans une URL, jamais dans un log.
:::

---

## La grille de cartes

Chaque secret est une **carte**. Elle affiche :

- le **nom** (en mono) ;
- un **badge type** ;
- un **badge rotation** (« rotation · N days ») lorsqu'une rotation est configurée ;
- un **badge expiration** — « expired », « expires today » ou « expires in N days ». L'alerte
  passe en **amber** à **14 jours ou moins** de l'échéance ;
- un pied de carte « ● stored · &lt;date de maj&gt; » ;
- les boutons **Edit** et **Delete** (la suppression demande une **confirmation inline**).

---

## Créer ou modifier un secret

Le bouton **+ New secret** — ou **Edit** sur une carte — ouvre le formulaire :

| Champ | Détail |
|-------|--------|
| **Name** | Identifiant du secret, contraint par `^[A-Z0-9_]{1,64}$`. **Non modifiable** en édition. |
| **Type** | **credential**, **ssh-key**, **key** ou **token**. |
| **Rotation** | Période de rotation, en **jours** (facultatif). Alimente le badge « rotation · N days ». |
| **Expires on** | Date d'expiration (facultatif). Alimente le badge d'expiration et l'alerte amber. |
| **Value** | La valeur secrète — champ **password**, en **écriture seule**. |

À l'enregistrement, l'interface envoie `POST /api/secrets` (réponse `204`), la valeur étant
transmise dans le **corps** de la requête, jamais dans l'URL. La suppression appelle
`DELETE /api/secrets/{name}`.

:::note Renommer ?
Le **nom** est la clé du secret dans le trousseau : il ne peut pas être changé après coup.
Pour « renommer », créez un nouveau secret et supprimez l'ancien.
:::

## Utiliser un secret dans un workflow

On ne colle jamais une valeur dans un workflow : on **référence** un secret par son nom, avec
la syntaxe **`${secret:NOM}`**. Dans l'[éditeur YAML](./editeur), ces références sont
**surlignées en amber** pour les distinguer d'une chaîne littérale.

```yaml
tasks:
  - id: fetch
    type: zosmf
    with:
      token: ${secret:ZOSMF_TOKEN}
```

Au moment de l'exécution, le binaire **résout** la référence en lisant le trousseau — la valeur
n'apparaît ni dans le YAML, ni dans l'[historique](./historique), ni dans les logs.

:::tip Mode App — secrets pré-provisionnés
En [mode App](../app/overview), les secrets sont **pré-provisionnés** par l'IT sur le poste et
résolus par le binaire. L'opérateur **ne saisit jamais** de secret : la surface App n'expose
même pas le panneau Secrets.
:::

## Équivalent CLI

Toutes les opérations du panneau existent en ligne de commande via `a4z secrets` (créer, lister
les noms et métadonnées, supprimer) — voir la [référence CLI](../cli-reference).
