# Exécuter un workflow

Le lancement d'un workflow ne se fait **pas** depuis un panneau dédié de l'éditeur.
Il se pilote depuis l'**en-tête du workflow** (la barre d'onglets **Overview /
Topology / Executions / Editor**), qui reste visible et actionnable **quel que soit
l'onglet ouvert**. On y trouve le bouton **Run**, le bouton **Stop** pendant
l'exécution, et un **badge d'état**.

Les runs s'exécutent **in-process** (aucun sous-process `a4z`) et sont enregistrés
avec le déclencheur `trigger = studio`.

| Badge | Signification |
| --- | --- |
| **Running…** | Le run est en cours. |
| **✓ Succeeded** | Le run s'est terminé avec succès. |
| **✕ Failed** | Le run a échoué. |
| **⊘ Cancelled** | Le run a été annulé (via **Stop**). |

## Lancer & arrêter

Le bouton **Run** est **désactivé tant que le schéma du workflow est invalide** ;
l'infobulle indique alors *« Fix the errors before running »*. Corrigez les erreurs
signalées dans l'[éditeur](./editeur) (ou le mode [no-code](./no-code)) pour le
réactiver.

Un clic sur **Run** **bascule automatiquement sur l'onglet Executions** et démarre le
run — **sauf** si des entrées ou des credentials sont requis : un **formulaire** prend
alors le relais avant tout lancement (voir ci-dessous).

Pendant l'exécution, le bouton **Stop** demande une **confirmation « Force stop? »**
avant d'interrompre le run (`POST /api/runs/{id}/cancel`). Le badge passe alors à
**⊘ Cancelled**.

:::info Où cliquer
**Run** et **Stop** vivent dans l'**en-tête du workflow**, pas dans l'éditeur. Vous
pouvez donc lancer et suivre un run tout en restant sur l'onglet **Editor**,
**Topology** ou **Overview**.
:::

## Refus & formulaires avant lancement

Au démarrage (`POST /api/runs`), le serveur **valide et complète** la demande **avant**
de lancer le moteur. Selon le cas :

| Situation | Comportement |
| --- | --- |
| **Workflow invalide** | Run **refusé** ; les diagnostics sont renvoyés. |
| **Entrées requises manquantes** | Un **formulaire d'inputs** s'affiche (`enum` → **select**, sinon champ **texte**). |
| **Secret `${secret:NOM}` non défini** | Run **refusé** : définissez d'abord le secret (voir [Secrets](./secrets)). |
| **Credentials z/OS manquants** | Un **formulaire user / mot de passe** est présenté. |

Les **credentials z/OS** ne sont demandés **que si le profil ne les fournit pas déjà**.
Ils sont **utilisés une seule fois** pour ce run et **jamais stockés**. Dans les logs,
les **mots de passe sont masqués** ; les **usernames** restent visibles.

## Suivi en direct

Une fois lancé, le run se suit dans l'onglet **Executions**. Le flux d'événements
**NDJSON** du moteur est diffusé via le WebSocket `/ws/runs/{id}` et alimente en temps
réel :

- des **logs défilants** ;
- une **Timeline (Gantt)** dont le repère **« now »** avance au fil de l'exécution ;
- la **vue DAG** de l'onglet **Topology**, qui reflète le **statut par nœud en direct**
  (en cours / réussi / échoué / annulé / ignoré).

À la fin du run, l'historique se recharge et le run terminé est **auto-sélectionné**.
La rétention d'historique s'applique après chaque run (voir [Paramètres](./settings)).

## Résultats & artefacts

À la fin du run, les **sorties par tâche** et la section **Artifacts** apparaissent dans
le détail. Les **artefacts** sont les fichiers détectés dans l'espace de travail
(ex. une archive) et sont proposés avec des **liens de téléchargement**.

Ces éléments restent consultables **même pour un run en échec** : les sorties
partielles produites avant l'incident sont conservées.
