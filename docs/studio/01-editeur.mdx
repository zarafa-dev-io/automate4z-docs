# Éditeur de workflow (mode Code)

Le mode **Code** présente l'éditeur YAML à gauche et un **volet latéral à deux onglets**
(**Topology** / **Documentation**) à droite. Un **split redimensionnable** sépare les deux.

En haut, la **barre de fichier** regroupe la bascule **Code / No-code**, l'indicateur de
validité **✓ schema valid** / **✕ N error(s)**, l'état d'enregistrement **● Modified** /
**Saved** (et **Saving…** pendant l'écriture) et le bouton **Save** (désactivé tant que le
fichier n'est pas modifié). Le raccourci **Ctrl/Cmd-S** enregistre.

## Édition

L'éditeur est bâti sur **CodeMirror 6** : numéros de ligne, **pliage** (folding) et
**historique** d'annulation/rétablissement.

La **coloration** distingue les clés, les chaînes (vert), les nombres et booléens (ambre)
et les commentaires (gris, italique). Deux formes de références sont **surlignées** pour
les repérer d'un coup d'œil :

| Référence | Rôle | Surlignage |
| --- | --- | --- |
| `${secret:…}` | Secret injecté au run (voir [Secrets](./secrets)) | **ambre gras** |
| `${{ … }}` | Expression évaluée | **violet** |

:::info Écriture verbatim
La sauvegarde (`Save` ou **Ctrl/Cmd-S**) est **atomique** et **verbatim** : vos commentaires,
l'ordre des clés et le style sont **préservés**, sans re-sérialisation du document.
:::

### Détection de conflit

À l'enregistrement, `POST /api/save` compare une **`revision`** (hash du contenu ouvert) à
celle du fichier sur disque. En cas de divergence, l'API répond **409** **sans écrire** et
un bandeau **« This file changed on disk since you opened it »** propose **Reload** (recharger
la version disque) ou **Overwrite** (écraser avec votre version).

## Autocomplétion guidée par le schéma

Les complétions proviennent du **schéma du binaire** (`GET /api/tasks`), donc toujours
alignées sur la version installée :

- les **types de tâches** sur `uses:`,
- les **champs** sur `with:` selon la tâche,
- les **clés** de workflow et de step.

## Validation & panneau Problems

Le contenu est validé en continu via `POST /api/validate`, qui couvre :

- l'**analyse YAML** (parse),
- la **conformité au schéma**,
- les **cycles du DAG**,
- des **avertissements** (non bloquants) pour chaque `${secret:NOM}` **non défini**.

Les **diagnostics** apparaissent **en ligne** dans la gouttière et sont regroupés dans un
**panneau Problems** sous l'éditeur : un clic **saute à la ligne** concernée. Les codes sont
alignés sur ceux de `a4z lint` (voir la [référence CLI](../cli-reference)) — par exemple
`A4Z-PARSE-001`, `A4Z-VAL-001`, `A4Z-DAG-001` / `A4Z-DAG-002`, `A4Z-SECRET-001`. L'indicateur
**✓ schema valid** / **✕ N error(s)** de la barre de fichier résume l'état.

## Volet latéral : Topology & Documentation

Le volet de droite offre deux onglets.

### Topology

Le **DAG** (graphe d'exécution) en **lecture seule** : steps, dépendances `needs` et
dépendances séquentielles implicites. Pendant une exécution, chaque nœud reflète le
**statut en direct** de la tâche, superposé au graphe.

:::tip Édition visuelle
La **Topology** est en lecture seule. Pour **modifier** le graphe (ajouter/supprimer des
tâches, tracer des dépendances), basculez en [mode No-code](./no-code).
:::

### Documentation

L'onglet **Documentation** affiche la doc de la tâche **sous le curseur**, selon l'état :

| État | Affichage |
| --- | --- |
| Curseur hors d'une tâche | « Place the cursor inside a task… » |
| Chargement | indicateur de chargement |
| Type inconnu | message d'erreur avec « Did you mean … ? » |
| Tâche reconnue | **type** + **résumé** + **Parameters** (dérivés du schéma, champs requis signalés) + **Examples** YAML |

:::note Air-gap
Toute la documentation provient du **binaire** : aucun accès réseau n'est requis.
:::
