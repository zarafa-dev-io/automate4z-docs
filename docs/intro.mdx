# automate4z

**automate4z** est un orchestrateur de workflows qui efface la frontière entre exécution mainframe z/OS et exécution locale.

Distribué comme **un binaire unique `a4z`** (Linux / macOS / Windows × amd64 / arm64), sans runtime à installer côté utilisateur — et **rien à installer côté z/OS non plus** : le mainframe est piloté via z/OSMF REST. Les workflows sont définis en YAML avec une syntaxe inspirée de GitHub Actions, adaptée au mainframe.

---

## Pourquoi automate4z ?

Les équipes COBOL en transition DevOps font face à un problème récurrent : leurs outils CI/CD modernes ne savent pas parler au mainframe. Chaque pipeline contient des scripts maison qui soumettent des jobs JCL, téléchargent des datasets et greppent des return codes — le tout sans type safety ni observabilité. Et les questions du quotidien — *que contient ce fichier ? pourquoi ce job a-t-il abendé ? que faut-il recompiler ?* — restent réservées à une session 3270.

automate4z résout ça avec un seul fichier YAML, un seul binaire, et une interface cohérente pour les deux mondes.

## Fonctionnalités clés

| Fonctionnalité | Description |
|----------------|-------------|
| **38 tâches built-in** | Shell, HTTP, filesystem, archives, notifications, requêtes JSON/YAML, templates, jobs et datasets z/OS — [le catalogue complet](task-reference/overview) |
| **Données mainframe** | Copybooks → schémas, jeux d'essai générés/anonymisés, lecture champ par champ, diff de datasets sur valeurs décodées |
| **Tests batch** | Le [bloc `tests:`](workflow-spec/gates-et-tests) : spool analysé, assertions, rapport JUnit lisible par Jenkins/GitLab |
| **Build incrémental** | `source-scan` → `build-impact` → `zos-build` : le pipeline façon DBB, [sans rien installer sur la LPAR](guides/build-and-test) |
| **Exécution DAG** | Dépendances entre steps résolues automatiquement ; steps indépendants en parallèle |
| **Expressions `$\{{ }}`** | Interpolation de contexte (inputs, outputs, env, runner) avec fonctions built-in |
| **[Le profil](profile)** | IA, connexions de transfert, notifications ; connexion z/OS via profils Zowe, trousseau OS ou variables d'env `A4Z_ZOS_*` ; secrets jamais dans le YAML |
| **IA sous gouvernance** | [`ai-prompt`](task-reference/ai-prompt) : un LLM explique un abend ou résume un listing — endpoints gouvernés par le profil, contexte anonymisé par construction, jamais décisionnaire |
| **Studio & mode App** | `a4z serve` ouvre une interface web locale ([le Studio](studio/overview)) ; `a4z run --ui` ouvre une surface opérateur verrouillée par workflow |
| **Plugins externes** | Tâches supplémentaires distribuées comme binaires `a4z-plugin-*`, découvertes dans des répertoires dédiés et verrouillables (`a4z plugins`) |
| **Lint + Plan** | Valide un workflow et affiche le plan d'exécution sans l'exécuter |
| **Binaire unique** | Pas de Node.js, Python ou Java requis — un seul exécutable cross-platform |

## Exemple minimal

```yaml
apiVersion: automate4z/v1
kind: Workflow
name: hello-world

inputs:
  name:
    type: string
    default: World

steps:
  - id: greet
    run: echo "Hello, ${{ inputs.name }}!"
```

```bash
a4z run hello.yml --input name=Alice
```

## Statut du projet

**Version courante : v{release.version}** ({release.date}) — 38 tâches built-in stables. Les tâches z/OS (`zos-jobs`, `zos-datasets`, `z-deps`) sont validées contre z/Xplore ; les lots récents couvrent les données mainframe (copybooks, jeux d'essai, inspection, comparaison), les tests batch (bloc `tests:` + JUnit), le build incrémental (`source-scan` / `build-impact` / `zos-build`), le Studio web, le mode App et les plugins externes.

Le détail de chaque version est sur la page [Notes de version](changelog) — mise à jour automatiquement à chaque release.
