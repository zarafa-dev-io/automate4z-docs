# Guide de démarrage

> Les **30 tâches built-in** (locales, z/OS, données mainframe, tests batch, build) sont stables — voir [le catalogue](task-reference/overview). Les fonctionnalités marquées **(v2)** dans la spec sont planifiées mais pas encore disponibles.

Extrayez et placez le binaire dans votre `PATH` :

```bash
tar -xzf automate4z_latest_linux_amd64.tar.gz
mv a4z /usr/local/bin/
```

### Compiler depuis les sources

Requiert Go 1.22 ou supérieur.

```bash
git clone https://github.com/zarafa-dev-io/automate4z.git
cd automate4z
go build -o a4z ./cmd/a4z
```

### Vérifier l'installation

```bash
a4z version
# a4z v1.1.2
```

## Votre premier workflow

Créez un fichier `hello.yml` :

```yaml
apiVersion: automate4z/v1
kind: Workflow
name: hello-world

inputs:
  name:
    type: string
    default: World

steps:
  - id: greet
    run: echo "Hello, ${{ inputs.name }}!"

  - id: done
    run: echo "Workflow terminé."
```

Lancez-le :

```bash
a4z run hello.yml
a4z run hello.yml --input name=Alice
```

Sortie attendue :

```
→ greet
  Hello, World!
✔ greet  0.12s

→ done
  Workflow terminé.
✔ done  0.08s

Summary:
  ✔ greet  0.12s
  ✔ done   0.08s
```

## Structure d'un workflow

Un workflow est un fichier YAML unique :

```yaml
apiVersion: automate4z/v1   # obligatoire
kind: Workflow               # obligatoire
name: mon-workflow           # obligatoire

inputs:                      # optionnel
  module:
    type: string
    required: true
    default: COBPRG01

env:                         # optionnel — variables d'env dans tous les steps
  TZ: Europe/Paris

defaults:                    # optionnel — valeurs with par défaut par type de tâche
  shell:
    shell: bash

steps:                       # obligatoire, ≥ 1 step
  - id: build
    name: Compilation
    run: make build

outputs:                     # optionnel
  exitCode:
    value: ${{ steps.build.outputs.exitCode }}
```

### Champs d'un step

| Champ | Requis | Description |
|-------|--------|-------------|
| `id` | oui | Identifiant unique dans le workflow |
| `name` | non | Libellé affiché (défaut : `id`) |
| `uses` | oui (sauf `run`) | Nom de la tâche built-in |
| `run` | oui (sauf `uses`) | Raccourci pour `uses: shell` |
| `with` | non | Paramètres de la tâche |
| `needs` | non | Dépendances explicites |
| `if` | non | Condition d'exécution |
| `env` | non | Variables d'env spécifiques au step |
| `timeout` | non | Durée max (ex : `30s`, `5m`, `1h`) |
| `continueOnError` | non | `true` pour continuer malgré l'échec du step — la clé de [l'idiome de gate](workflow-spec/gates-et-tests) |

Au-delà de `steps:`, un workflow peut aussi porter un bloc [`tests:`](workflow-spec/gates-et-tests) (cas de test batch : setup / execute / assert) et un bloc `ui:` (surface opérateur du mode App).

## Parallélisme et DAG

### Comportement par défaut : séquentiel

Sans `needs`, les steps s'exécutent dans **l'ordre de déclaration**.

### Dépendances explicites avec `needs`

```yaml
steps:
  - id: fetch
    run: ./fetch-sources.sh

  - id: compile
    needs: [fetch]
    run: make compile

  - id: test
    needs: [fetch]       # parallèle avec compile
    run: make test

  - id: publish
    needs: [compile, test]   # attend les deux
    run: make publish
```

`a4z plan` affiche les niveaux d'exécution :

```
Level 1:  fetch
Level 2:  compile, test     ← parallèles
Level 3:  publish
```

## Contrôle d'exécution

### Condition `if`

```yaml
# Exécuter uniquement en cas d'échec
- id: notify-failure
  if: ${{ failure() }}
  uses: http
  with:
    method: POST
    url: https://hooks.example.com/alert

# Toujours exécuter (même après un échec)
- id: cleanup
  if: ${{ always() }}
  run: rm -rf ./tmp

# Condition sur un input
- id: publish-sonar
  if: ${{ inputs.publishSonar == true }}
  run: sonar-scanner
```

### Timeout

```yaml
- id: long-job
  timeout: 10m
  run: ./batch.sh
```

### `continueOnError`

```yaml
- id: optional-step
  continueOnError: true
  run: ./generate-report.sh
```

## Secrets

Deux mécanismes, jamais de secret dans le YAML :

- **Variables d'environnement** préfixées `A4Z_SECRET_` — leurs valeurs sont masquées (`***`) dans les logs ;
- **Trousseau de l'OS** via [`a4z secrets`](cli-reference#a4z-secrets) (`set` / `list` / `delete`) — référencées par `${secret:NOM}` dans les profils.

```bash
export A4Z_SECRET_API_TOKEN="ghp_xxxxx"
a4z run deploy.yml
```

Dans le workflow :

```yaml
- id: call-api
  uses: http
  with:
    url: https://api.example.com/deploy
    headers:
      Authorization: Bearer ${{ env.A4Z_SECRET_API_TOKEN }}
```

## Historique des runs (SQLite)

`a4z` journalise chaque exécution dans une base **SQLite** locale :

```
<racine du dépôt Git>/.automate4z/runs.db
```

- **Un emplacement prévisible par dépôt** : la base est ancrée à la racine du dépôt Git englobant (hors dépôt Git : le répertoire du workflow). Le CLI et le Studio partagent le même historique.
- **Contenu** : les runs (statut, inputs résolus, durées, code de sortie), leurs steps (statuts, RC, raisons de skip), leurs outputs nommés et leurs lignes de log. **Les valeurs de secrets sont masquées avant écriture** — jamais stockées en clair.
- **Aucun service externe** : driver SQLite en Go pur (pas de cgo), la base reste un simple fichier local mono-utilisateur.
- **Rotation** : `--keep-runs` (défaut 50) borne l'historique conservé.

Interroger l'historique — trois portes d'entrée :

```bash
a4z runs list                       # les runs, du plus récent au plus ancien
a4z runs show 01HZ4K3Q2R…          # le détail d'un run : steps, RC, durées
a4z run wf.yml --resume 01HZ4K…    # reprendre en sautant les steps déjà réussis
```

…ou l'onglet **Historique** du [Studio](studio/overview), qui lit la même base.

Les **fichiers** produits par vos tâches (rapports NDJSON, listings, `junit.xml`…) restent des fichiers ordinaires aux chemins que vos workflows choisissent — la base ne stocke que le journal. Les artefacts d'exécution internes (sorties de plugins, notamment) vont sous `.automate4z/runs/<run-id>/<step-id>/`.

:::tip
Ajoutez `.automate4z/` à votre `.gitignore` : l'historique de runs est un état local, pas du code.
:::

## Explorer depuis le terminal

Le binaire embarque sa propre documentation — pas besoin de quitter le terminal :

```bash
a4z schema --list-tasks       # les 30 tâches, avec leur catégorie et leur résumé
a4z docs data-compare         # la doc d'une tâche (inputs, outputs, exemples)
a4z schema --task zos-jobs    # le JSON Schema des inputs d'une tâche
a4z runs list                 # l'historique des exécutions du workspace
```

## L'interface web (Studio)

Tout ce que fait le CLI se fait aussi dans le navigateur :

```bash
a4z serve                     # ouvre le Studio sur http://127.0.0.1:4500
```

Le Studio édite les workflows (formulaires ou YAML), les exécute, montre l'historique et les résultats — voir la [section Studio](studio/overview). Pour donner un workflow à un opérateur non-développeur, le **mode App** (`a4z run <wf> --ui`) ouvre une surface verrouillée limitée aux inputs déclarés dans le bloc `ui:` du workflow.

## Codes de sortie

| Code | Signification |
|------|---------------|
| `0` | Succès |
| `1` | Échec métier (lint avec erreurs, run avec step en échec) |
| `2` | Erreur interne (fichier introuvable, YAML invalide) |

## Exemple complet — Pipeline CI locale

```yaml
apiVersion: automate4z/v1
kind: Workflow
name: ci-local
description: Pipeline CI locale — lint, build, tests, notification.

inputs:
  repo:
    type: string
    default: .
  notify:
    type: boolean
    default: false

steps:
  - id: vet
    uses: shell
    with:
      run: go vet ./...
      workdir: ${{ inputs.repo }}

  - id: lint
    uses: shell
    with:
      run: golangci-lint run ./...
      workdir: ${{ inputs.repo }}
      timeout: 3m

  - id: build
    needs: [vet, lint]
    run: go build -o ./bin/app ./cmd/app
    timeout: 5m

  - id: test
    needs: [vet, lint]
    uses: shell
    with:
      run: go test -race -count=1 ./...
      workdir: ${{ inputs.repo }}
      timeout: 10m

  - id: notify-ok
    needs: [build, test]
    if: ${{ success() && inputs.notify == true }}
    uses: http
    with:
      method: POST
      url: https://hooks.example.com/ci
      body:
        status: success
        workflow: ${{ workflow.name }}
        runId: ${{ workflow.runId }}

  - id: notify-fail
    needs: [build, test]
    if: ${{ failure() && inputs.notify == true }}
    uses: http
    with:
      method: POST
      url: https://hooks.example.com/ci
      body:
        status: failure
        workflow: ${{ workflow.name }}
```

```bash
a4z lint ci-local.yml
a4z plan ci-local.yml --input notify=true
a4z run  ci-local.yml --input notify=true --parallelism 2
```
