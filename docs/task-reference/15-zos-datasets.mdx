# `zos-datasets` — Datasets MVS et fichiers USS

Opérations complètes sur les **datasets MVS** z/OS (séquentiels, PDS, PDSE) et les **fichiers USS** (Unix System Services), via l'API REST z/OSMF : transferts, allocation, listing, copie et renommage serveur-side, gestion HSM (migration/rappel), tags d'encodage, permissions.

```yaml
- uses: zos-datasets
  with:
    action: upload
    localPath: ./src/cobol
    dataset: USER.MYAPP.SRC
    lpar: dev01
```

## Comprendre la tâche en 60 secondes

- **Une tâche, seize actions.** `action:` sélectionne l'opération — même modèle que `fs`, `s3` ou `ftp`.
- **MVS ou USS ?** Si le step contient `ussPath`, la cible est un fichier Unix (chemin absolu commençant par `/`). Si le step contient `dataset`, la cible est un dataset MVS. Les actions `mkdir`, `chmod`, `chtag`, `chown` et `move` sont USS-only ; `migrate`, `recall` et `deleteMigrated` sont MVS-only.
- **La session est gérée pour vous.** La tâche ne se connecte jamais elle-même : elle consomme la session z/OSMF ouverte **une fois par run et par LPAR** (profil `lpar:`). Un mot de passe à usage unique fonctionne. Les credentials ne sont jamais dans le workflow, jamais loggés.
- **Les transferts streament.** Un download écrit directement sur disque (pas de mise en mémoire du dataset entier) ; en cas d'échec en cours de route, le fichier partiel est supprimé — jamais de fichier tronqué qui a l'air complet.
- **Les opérations serveur-side ne font pas transiter les données.** `copy`, `rename`, `move`, HSM : tout se passe sur le LPAR, le poste n'échange que des ordres.
- **Rien n'est deviné.** L'encodage est votre déclaration (`encoding`, `binary`, `chtag`), le rappel HSM est votre choix (`migratedRecall`), un chemin USS se reconnaît à son `/` initial (un nom de dataset MVS ne peut pas commencer par `/` — c'est une règle de grammaire, pas une heuristique).

## Les trois pièges classiques (à lire avant le premier workflow)

**1. L'encodage.** Un mainframe vit en EBCDIC (IBM-1047 le plus souvent), votre poste en UTF-8/ASCII. Par défaut, z/OSMF convertit le texte dans les deux sens — c'est ce qu'il faut pour du source COBOL ou du JCL. Mais pour un **load module, un tar, un zip ou tout binaire** : `binary: true`, sinon la conversion mutile le fichier. Et pour un encodage spécifique (fichier déjà en IBM-1047, UTF-8 à préserver…) : `encoding: IBM-1047`.

**2. Le tag USS.** Sur USS, chaque fichier porte (ou devrait porter) un **tag** qui déclare son encodage. Un fichier uploadé sans tag sera mal interprété par les outils Unix du mainframe (`cat` illisible, shell script qui ne s'exécute pas). Après un upload USS, posez le tag avec `action: chtag` — voir l'exemple de déploiement complet plus bas.

**3. La migration HSM.** Sur un vrai système de production, les datasets peu utilisés sont **migrés** (déplacés vers un stockage secondaire par HSM). Un `download` d'un dataset migré échoue par défaut. Trois réponses possibles : `migratedRecall: wait` sur le download (rappeler et attendre), une action `recall` explicite en début de workflow, ou `migratedRecall: error` pour échouer proprement.

## Actions MVS

### `upload` — poste → dataset

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `dataset` | string | oui | Dataset cible. Pour un PDS sans membre spécifié, chaque fichier local devient un membre. |
| `localPath` | string | oui | Fichier **ou répertoire** local (relatif au répertoire du workflow). |
| `encoding` | string | non | Codepage source. Vide = conversion EBCDIC automatique (bon pour du source). |
| `binary` | boolean | non | `true` = transfert binaire sans conversion. Défaut `false`. |

**Upload d'un répertoire vers un PDS** : chaque fichier devient un membre. Le nom de membre est dérivé du nom de fichier : extension supprimée → majuscules → caractères invalides supprimés → tronqué à 8 → préfixe `A` si le premier caractère est un chiffre (`customer-record.cbl` → `CUSTOMER`, `01-header.cbl` → `A01HEADE`). Deux fichiers qui produisent le même membre font échouer le step **avant tout transfert** (`ErrMemberNameCollision`).

### `download` — dataset → poste

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `dataset` | string | oui | Dataset ou membre (`USER.SRC(MEMBER)`) ; avec `memberPattern`, nom du PDS sans membre. |
| `localPath` | string | oui | Destination locale ; avec `memberPattern`, répertoire cible (créé si absent). |
| `encoding` | string | non | Codepage. |
| `binary` | boolean | non | Transfert binaire. Défaut `false`. |
| `memberPattern` | string | non | **Download de masse** : chaque membre du PDS correspondant au pattern ISPF (`*` = tous, `PAY*`…) devient un fichier dans `localPath`. Filtre appliqué côté z/OSMF. |
| `extension` | string | non | Avec `memberPattern` : extension ajoutée aux fichiers (`cbl` → `PAYROLL.cbl`). |
| `migratedRecall` | string | non | Si le dataset est **migré** : `wait` (rappeler et attendre), `nowait` (rappeler sans attendre), `error` (échouer). Absent = défaut du serveur. |

Le download de masse écrit les membres en ordre alphabétique (déterministe). En cas d'échec en cours de route, le fichier partiel est supprimé mais les membres déjà écrits restent ; un pattern sans correspondance réussit avec `membersDownloaded: 0`.

### `create` — allocation

| Champ | Type | Requis | Défaut | Description |
|-------|------|--------|--------|-------------|
| `dataset` | string | oui | — | Nom (44 chars max, qualifiers de 8 max). |
| `datasetType` | string | non | `seq` | `seq`, `pds`, ou `pdse` — `pdse` alloue un **vrai LIBRARY** (`dsntype: LIBRARY`). |
| `recfm` | string | non | `FB` | `FB`, `VB`, `F`, `U`, `FBA`, `VBA`. |
| `lrecl` | integer | non | `80` | Longueur d'enregistrement. |
| `blksize` | integer | non | `lrecl × 10` (FB) | Taille de bloc. |
| `primary` / `secondary` | integer | non | `1` / `1` | Allocation en `alcunit`. |
| `dirblk` | integer | non | `10` | Blocs de répertoire (PDS). |
| `alcunit` | string | non | `TRK` | `TRK` (pistes) ou `CYL` (cylindres). |
| `volser` | string | non | — | Volume explicite (contourne le placement SMS). |
| `dataclass` / `storclass` / `mgmtclass` | string | non | — | Classes **SMS**. Sur un site SMS-managé, c'est souvent la seule chose à fournir. |
| `like` | string | non | — | **Dataset modèle** : les attributs non fournis sont hérités du modèle, les attributs explicites l'emportent. Les défauts de la tâche ne sont pas envoyés dans ce cas. |

### `delete`

| Champ | Type | Requis |
|-------|------|--------|
| `dataset` | string | oui — dataset entier ou `PDS(MEMBER)` pour un seul membre |

### `list` — catalogue et membres

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `pattern` | string | l'un des deux | Sans `membersOf` : pattern ISPF de datasets (`USER.MYAPP.*`). Avec `membersOf` : filtre optionnel sur les noms de membres (`PAY*`), côté z/OSMF. |
| `membersOf` | string | l'un des deux | Liste les membres de ce PDS (avec stats ISPF : `version`, `modDate`, `user`). |
| `metadata` | boolean | non | Avec `pattern` : ajoute les attributs étendus du catalogue — `cdate` (création), `rdate` (dernière référence), `edate` (expiration), `dsntp`, `used` (%), `extents`, `size` (tracks), `spaceUnits`. Plus coûteux sur un gros catalogue. Les datasets **migrés** retournent ces champs vides, sans déclencher de rappel HSM. |

:::tip Pourquoi pas de date de modification ?
MVS ne conserve **aucune date de modification** au niveau dataset. `rdate` (dernière *référence*, qui bouge aussi en lecture) est le signal le plus proche ; la vraie date de modification n'existe que pour les **membres de PDS** (`membersOf` → `modDate`, tenue par les stats ISPF).
:::

### `exists`

| Champ | Type | Requis |
|-------|------|--------|
| `dataset` | string | oui — dataset ou membre (`USER.PDS(MBR)`) |

Retourne `exists` (bool, un 404 n'est **pas** une erreur) et `datasetType` (`seq`, `pds`, ou `member`). Idiome : garder un `create` derrière un `if:` — voir les exemples.

### `copy` — copie serveur-side (datasets **et** croisement USS)

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `source` | string | oui | Dataset, membre, `PDS(*)` (tous les membres) ou chemin USS (commence par `/`). |
| `target` | string | oui | Dataset, membre ou chemin USS. |
| `replace` | boolean | non | Écraser un membre cible existant. Défaut `false` — un membre existant fait **échouer** la copie. |
| `binary` | boolean | non | USS → dataset : le fichier source est binaire. |

Trois croisements : **dataset → dataset** (y compris `USER.SRC(*)` → PDS pour copier tous les membres), **USS → dataset**, **dataset → USS**. USS → USS est refusé (utilisez `move` ou les actions USS). Tout est serveur-side : rien ne transite par le poste.

### `rename` — renommage natif, datasets **et membres**

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `source` | string | oui | Dataset ou membre. |
| `target` | string | oui | Dataset ou membre (même PDS pour un membre). |

Utilise le **rename natif z/OSMF** (z/OS 2.2+) : atomique, attributs préservés. Source et cible doivent être toutes deux des datasets ou toutes deux des membres ; un rename de membre reste dans le même PDS. Une cible existante fait échouer le step **sans toucher la source**.

### `migrate` / `recall` / `deleteMigrated` — HSM

| Champ | Type | Requis | Défaut | Description |
|-------|------|--------|--------|-------------|
| `dataset` | string | oui | — | Dataset cible. |
| `wait` | boolean | non | `false` (migrate), `true` (recall, deleteMigrated) | Attendre la fin de l'opération HSM. `recall` attend par défaut : on rappelle pour utiliser le dataset au step suivant. |
| `purge` | boolean | non | `false` | `deleteMigrated` : ne pas garder de copie de sauvegarde HSM. |

`migrate` archive (geste non bloquant par défaut), `recall` ramène un dataset migré sur le stockage primaire, `deleteMigrated` supprime **sans rappeler** — précieux pour purger des générations archivées sans payer le rappel.

## Actions USS

### `upload` / `download` (USS)

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `ussPath` | string | oui | Chemin USS absolu. |
| `localPath` | string | oui | Chemin local. |
| `encoding` | string | non | Codepage. |
| `binary` | boolean | non | Transfert binaire. |

:::caution Après un upload USS, taguez le fichier
L'upload écrit les octets mais ne pose pas de tag : enchaînez avec `action: chtag` pour déclarer l'encodage, sinon les outils Unix du LPAR liront le fichier avec l'encodage par défaut du système. Voir l'exemple « Déploiement USS complet ».
:::

### `chmod`

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|

| `recursive` | boolean | non | Défaut `false`. |

### `chtag` — déclarer l'encodage d'un fichier

Le **tag** est ce qui dit à USS comment interpréter les octets d'un fichier. Le codeset est **votre déclaration, jamais deviné**.

| Champ | Type | Requis | Défaut | Description |
|-------|------|--------|--------|-------------|
| `ussPath` | string | oui | — | Cible. |
| `tagType` | string | non | `text` | `text`, `binary`, `mixed`. |
| `codeset` | string | requis pour `text`/`mixed` | — | `IBM-1047`, `ISO8859-1`, `UTF-8`, … |
| `remove` | boolean | non | `false` | `true` = détaguer. |
| `recursive` | boolean | non | `false` | Appliquer à l'arborescence. |

### `chown`

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `ussPath` | string | oui | Cible. |
| `owner` | string | oui | Nouveau propriétaire. |
| `group` | string | non | Nouveau groupe. |
| `recursive` | boolean | non | Défaut `false`. |

### `move` (USS)

| Champ | Type | Requis | Description |
|-------|------|--------|-------------|
| `source` | string | oui | Chemin USS absolu. |
| `target` | string | oui | Nouveau chemin USS absolu. |

Rename/déplacement serveur-side, répertoires compris. Pour un dataset, utilisez `rename`.

## Outputs

| Action | Outputs |
|--------|---------|
| `upload` MVS | `bytesTransferred`, `membersWritten` (upload dir→PDS) |
| `upload` USS | `bytesTransferred` |
| `download` | `bytesTransferred`, `localPath` ; avec `memberPattern` : `membersDownloaded` |
| `create` | `created` (bool) |
| `delete` / `deleteMigrated` | `deleted` (bool) (+ `waited` pour deleteMigrated) |
| `list` MVS | `datasets` ou `members` (array), `count` ; avec `metadata: true` : `cdate`, `rdate`, `edate`, `dsntp`, `used`, `extents`, `size`, `spaceUnits` |
| `list` USS | `entries` (array de `{ name, path, size, isDir, mode }`), `count` |
| `exists` MVS | `exists` (bool), `datasetType` (`seq`, `pds`, `member`) |
| `exists` USS | `exists` (bool), `type` (`file`, `dir`, `symlink`) |
| `copy`, `rename`, `chmod`, `chtag`, `chown` | `success` (bool) |
| `migrate`, `recall` | `success` (bool), `waited` (bool) |
| `mkdir` | `created` (bool), `ussPath` |
| `move` | `success` (bool), `ussPath` (nouveau chemin) |

## Erreurs typées

| Erreur | Description |
|--------|-------------|
| `ErrInvalidDatasetName` | Nom qui viole les règles MVS (44 chars, qualifiers de 8, premier caractère non numérique). |
| `ErrDatasetNotFound` | Dataset introuvable (download, delete, rename, HSM). |
| `ErrDatasetExists` | `create` ou `rename` vers un nom déjà pris. |
| `ErrMemberNotFound` | Membre PDS introuvable (rename de membre). |
| `ErrMemberNameCollision` | Deux fichiers locaux produisent le même nom de membre. |
| `ErrTransferFailed` | Échec upload/download (le fichier partiel a été supprimé). |
| `ErrAllocationFailed` | `create` refusé par z/OSMF (attributs incohérents, espace, RACF). |
| `ErrUssPathNotFound` | Chemin USS introuvable. |
| `ErrUssPermission` | Opération USS refusée (RACF/permissions). |

## Recettes de workflows

### 1. Chaîne de build : sources locales → PDS, en masse

```yaml
apiVersion: automate4z/v1
kind: Workflow
name: push-sources
steps:
  - id: push
    uses: zos-datasets
    with:
      action: upload
      localPath: ./src/cobol          # répertoire → un membre par fichier
      dataset: USER.MYAPP.SRC
      lpar: dev01

  - run: echo "${{ steps.push.outputs.membersWritten }} membres poussés"
```

### 2. Récupérer tout un PDS pour revue ou sauvegarde locale

```yaml
steps:
  - id: pull
    uses: zos-datasets
    with:
      action: download
      dataset: USER.MYAPP.SRC
      memberPattern: "*"              # ou PAY* pour un sous-ensemble
      localPath: ./backup/src
      extension: cbl                  # PAYROLL → backup/src/PAYROLL.cbl

  - run: echo "${{ steps.pull.outputs.membersDownloaded }} membres, ${{ steps.pull.outputs.bytesTransferred }} octets"
```

### 3. Allocation conditionnelle — SMS, PDSE, ou par modèle

```yaml
steps:
  - id: check
    uses: zos-datasets
    with:
      action: exists
      dataset: USER.MYAPP.LOAD

  # Site SMS-managé : les classes suffisent, SMS place le dataset
  - if: ${{ steps.check.outputs.exists == false }}
    uses: zos-datasets
    with:
      action: create
      dataset: USER.MYAPP.LOAD
      datasetType: pdse               # un vrai LIBRARY
      recfm: U
      lrecl: 0
      blksize: 32760
      storclass: SCPROD
      mgmtclass: MCSTD

  # Variante : cloner les attributs d'un dataset existant
  - uses: zos-datasets
    with:
      action: create
      dataset: USER.MYAPP.SRC.V2
      like: USER.MYAPP.SRC            # attributs hérités du modèle
```

### 4. Promotion atomique par rename — l'idiome « blue/green » des membres

```yaml
steps:
  # Le nouveau module est déjà uploadé sous un nom candidat
  - uses: zos-datasets
    with:
      action: rename
      source: USER.PROD.LOAD(NEWMAIN)
      target: USER.PROD.LOAD(MAIN)    # échoue si MAIN existe : le supprimer d'abord,
                                      # ou renommer MAIN vers OLDMAIN pour garder un retour arrière
```

```yaml
  # Rotation avec retour arrière possible :
  - uses: zos-datasets
    with: { action: rename, source: "USER.PROD.LOAD(MAIN)", target: "USER.PROD.LOAD(MAINPREV)" }
  - uses: zos-datasets
    with: { action: rename, source: "USER.PROD.LOAD(NEWMAIN)", target: "USER.PROD.LOAD(MAIN)" }
```

### 5. HSM : rappeler avant de lire, archiver après

```yaml
steps:
  # Option A — rappel implicite pendant le download
  - uses: zos-datasets
    with:
      action: download
      dataset: PROD.ARCHIVE.Y2024
      localPath: ./work/archive.dat
      migratedRecall: wait            # rappelle et attend si migré

  # Option B — rappel explicite (contrôle du wait), puis traitement
  - uses: zos-datasets
    with:
      action: recall
      dataset: PROD.ARCHIVE.Y2024     # wait: true par défaut

  # Archiver un dataset de travail en fin de chaîne (non bloquant)
  - uses: zos-datasets
    with:
      action: migrate
      dataset: USER.MYAPP.WORK.OUTPUT

  # Purger une génération archivée sans la rappeler
  - uses: zos-datasets
    with:
      action: deleteMigrated
      dataset: PROD.ARCHIVE.Y2019
      purge: true
```

### 6. Copies croisées dataset ↔ USS, sans transfert local

```yaml
steps:
  # Un rapport produit par un batch MVS, à traiter avec des outils Unix
  - uses: zos-datasets
    with:
      action: copy
      source: PROD.BATCH.REPORT
      target: /u/batch/reports/report.txt

  # L'inverse : un fichier généré sous USS, à ranger dans un PDS
  - uses: zos-datasets
    with:
      action: copy
      source: /u/batch/out/summary.txt
      target: USER.MYAPP.REPORTS(SUMMARY)
      replace: true                   # écrase la version précédente
```

### 7. Sauvegarde d'un PDS avant modification (wildcard membre)

```yaml
steps:
  - uses: zos-datasets
    with:
      action: create
      dataset: USER.MYAPP.SRC.BAK
      like: USER.MYAPP.SRC

  - uses: zos-datasets
    with:
      action: copy
      source: USER.MYAPP.SRC(*)       # tous les membres, serveur-side
      target: USER.MYAPP.SRC.BAK
      replace: true
```

### 8. Déploiement USS complet : mkdir → upload → chtag → chmod → chown

```yaml
steps:
  - uses: zos-datasets
    with:
      action: mkdir
      ussPath: /u/deploy/myapp/bin    # recursive: true par défaut (mkdir -p)

  - uses: zos-datasets
    with:
      action: upload
      ussPath: /u/deploy/myapp/bin/run.sh
      localPath: scripts/run.sh

  - uses: zos-datasets
    with:
      action: chtag                   # déclarer l'encodage : sans tag, le shell
      ussPath: /u/deploy/myapp/bin/run.sh
      tagType: text
      codeset: IBM-1047               # ne saura pas lire le script

  - uses: zos-datasets
    with:
      action: chmod
      ussPath: /u/deploy/myapp/bin/run.sh
      mode: "0755"

  - uses: zos-datasets
    with:
      action: chown
      ussPath: /u/deploy/myapp
      owner: batchusr
      group: batchgrp
      recursive: true
```

### 9. Ménage piloté par le catalogue : supprimer les vieilles générations

```yaml
steps:
  - id: backups
    uses: zos-datasets
    with:
      action: list
      pattern: PROD.BACKUP.*
      metadata: true                  # cdate, size, dsntp…

  # Les datasets créés avant 2025, triés par date de création
  - id: old
    uses: json-query
    with:
      content: ${{ steps.backups.outputs.datasets }}
      query: '[.[] | select(.cdate != "" and .cdate < "2025/01/01") | .name]'

  - forEach: ${{ steps.old.outputs.result }}
    as: ds
    uses: zos-datasets
    with:
      action: delete
      dataset: ${{ ds }}
```

### 10. Publication binaire : load module poussé sans corruption

```yaml
steps:
  - uses: zos-datasets
    with:
      action: upload
      localPath: ./dist/MYMOD.load
      dataset: USER.PROD.LOAD(MYMOD)
      binary: true                    # OBLIGATOIRE pour un load module
```

### 11. Réorganisation USS serveur-side

```yaml
steps:
  - uses: zos-datasets
    with:
      action: move                    # rename/déplacement, répertoires compris
      source: /u/deploy/myapp
      target: /u/deploy/myapp-v2
```

### 12. Inventaire filtré des membres, sans tout lister

```yaml
steps:
  - id: pay-members
    uses: zos-datasets
    with:
      action: list
      membersOf: USER.MYAPP.SRC
      pattern: PAY*                   # filtre côté z/OSMF

  - run: echo "${{ steps.pay-members.outputs.count }} modules paie"
```

## Erreurs courantes

- **Collision de noms de membres** — `customer.cbl` et `customer.jcl` donnent tous deux `CUSTOMER`. Renommer côté local ; la collision est détectée avant tout transfert.
- **Encodage corrompu** — un binaire uploadé sans `binary: true` est mutilé par la conversion EBCDIC. Load modules, tar, zip : toujours `binary: true`.
- **Fichier USS illisible après upload** — le tag manque. Enchaîner `chtag` avec le bon `codeset`.
- **Download qui échoue sur un dataset migré** — ajouter `migratedRecall: wait` ou une action `recall` en amont.
- **`copy` de membre qui échoue** — la cible existe et `replace` n'est pas posé. C'est voulu : l'écrasement est un choix explicite.
- **`ErrDatasetExists` sur `create`** — protéger avec `exists` + `if:`, ou accepter avec `continueOnError`.
- **403 (`ErrUssPermission`/`ErrZosmfForbidden`)** — profil RACF insuffisant pour la ressource ; ce n'est pas un problème d'authentification.

## FAQ

**Pourquoi `create` n'est-il pas automatique à l'upload ?** Parce qu'allouer implique des choix (recfm, lrecl, SMS) que la tâche refuse de deviner. L'idiome `exists` + `if:` + `create` rend l'intention explicite et le workflow rejouable.

**`pds` ou `pdse` ?** `pdse` (LIBRARY) : pas de compression nécessaire, plus de membres, c'est le choix moderne. `pds` reste utile pour des chaînes legacy qui l'exigent.

**Comment lister tous les HLQ d'un user ?** `action: list` avec `pattern: USER.*` (ou `USER.**` selon la profondeur).

**Les transferts sont-ils rejoués en cas d'erreur réseau ?** Les erreurs transitoires sont retentées avant que le corps commence à circuler ; une fois le transfert entamé, un échec est final (le fichier partiel est supprimé) — relancer le step est sûr.

**Où mettre les credentials ?** Nulle part dans le workflow. Le profil LPAR référence le trousseau natif ou des variables d'environnement ; la session est ouverte une fois par run.
