# Tâches built-in

automate4z embarque **38 tâches built-in** dans le binaire `a4z`. Elles se composent librement dans un même workflow — c'est même la philosophie du produit : chaque tâche fait une chose, et les scénarios riches (tester un batch, builder à l'impact) sont des **compositions** documentées, pas des boîtes noires.

## Conventions transverses

### Outputs implicites

Chaque step expose automatiquement ces trois outputs, quelle que soit la tâche :

| Output | Type | Description |
|--------|------|-------------|
| `exitCode` | integer | Code de retour (0 = succès) |
| `duration` | string | Durée d'exécution (format Go, ex : `1.23s`) |
| `status` | string | `success`, `failure`, `skipped` ou `cancelled` |

### Chemins relatifs

Les chemins relatifs sont résolus par rapport au **répertoire du fichier workflow YAML**, pas au CWD du processus `a4z`.

### Profils z/OS

Les tâches `zos-*` et `z-deps` résolvent leurs credentials via le profil indiqué par `--profile <name>` au lancement, ou le profil `default` (`~/.automate4z/profiles/<name>.yml` + trousseau natif pour les secrets).

### Encodages

Les transferts entre poste local (UTF-8) et z/OS (EBCDIC) sont gérés par les adaptateurs avec un défaut sensé et une option `encoding` explicite. Les tâches données (`data-inspect`, `data-compare`, `testdata-generate`…) partagent les mêmes tables EBCDIC embarquées : `ibm-1047`, `cp037`, `cp1140`, `cp297`, `cp1147`, `cp500`, `cp1148`.

### Gates et verdicts

Beaucoup de tâches récentes (`assert`, `data-compare`, `job-assert`, `build-impact`, `zos-build`…) distinguent **« le contrôle a échoué »** (le résultat est là, il est mauvais) de **« le contrôle n'a pas pu tourner »** (panne technique). Ce contrat — et l'idiome `continueOnError` + `if:` qui va avec — est expliqué une fois pour toutes dans [Gates, verdicts et tests](../workflow-spec/gates-et-tests).
