# Getting started

## Your first workflow

Create a file `hello.yml`:

```yaml
apiVersion: automate4z/v1
kind: Workflow
name: hello-world

inputs:
  name:
    type: string
    default: World

steps:
  - id: greet
    run: echo "Hello, ${{ inputs.name }}!"

  - id: done
    run: echo "Workflow complete."
```

Run it:

```bash
a4z run hello.yml
a4z run hello.yml --input name=Alice
```

Expected output:

```
→ greet
  Hello, World!
✔ greet  0.12s

→ done
  Workflow complete.
✔ done  0.08s

Summary:
  ✔ greet  0.12s
  ✔ done   0.08s
```

## Workflow structure

A workflow is a single YAML file:

```yaml
apiVersion: automate4z/v1   # required
kind: Workflow               # required
name: my-workflow            # required

inputs:                      # optional
  module:
    type: string
    required: true
    default: COBPRG01

env:                         # optional — env vars injected in all steps
  TZ: Europe/Paris

defaults:                    # optional — default with values per task type
  shell:
    shell: bash

steps:                       # required, ≥ 1 step
  - id: build
    name: Compilation
    run: make build

outputs:                     # optional
  exitCode:
    value: ${{ steps.build.outputs.exitCode }}
```

### Step fields

| Field | Required | Description |
|-------|----------|-------------|
| `id` | yes | Unique identifier within the workflow |
| `name` | no | Label shown in logs (default: `id`) |
| `uses` | yes (unless `run`) | Built-in task name |
| `run` | yes (unless `uses`) | Shorthand for `uses: shell` |
| `with` | no | Task parameters |
| `needs` | no | Explicit dependencies |
| `if` | no | Execution condition |
| `env` | no | Step-specific env vars |
| `timeout` | no | Max duration (e.g. `30s`, `5m`, `1h`) |
| `continueOnError` | no | `true` to continue despite a step failure — the key to [the gate idiom](workflow-spec/gates-et-tests) |

Beyond `steps:`, a workflow can also carry a [`tests:`](workflow-spec/gates-et-tests) block (batch test cases: setup / execute / assert) and a `ui:` block (the App mode operator surface).

## Parallelism and DAG

### Default behavior: sequential

Without `needs`, steps run in **declaration order**.

### Explicit dependencies with `needs`

```yaml
steps:
  - id: fetch
    run: ./fetch-sources.sh

  - id: compile
    needs: [fetch]
    run: make compile

  - id: test
    needs: [fetch]       # parallel with compile
    run: make test

  - id: publish
    needs: [compile, test]   # waits for both
    run: make publish
```

`a4z plan` shows execution levels:

```
Level 1:  fetch
Level 2:  compile, test     ← parallel
Level 3:  publish
```

## Execution control

### Condition `if`

```yaml
# Run only on failure
- id: notify-failure
  if: ${{ failure() }}
  uses: http
  with:
    method: POST
    url: https://hooks.example.com/alert

# Always run (even after failure)
- id: cleanup
  if: ${{ always() }}
  run: rm -rf ./tmp

# Condition on an input
- id: publish-sonar
  if: ${{ inputs.publishSonar == true }}
  run: sonar-scanner
```

### Timeout

```yaml
- id: long-job
  timeout: 10m
  run: ./batch.sh
```

### `continueOnError`

```yaml
- id: optional-step
  continueOnError: true
  run: ./generate-report.sh
```

## Secrets

Two mechanisms, never a secret in the YAML:

- **Environment variables** prefixed with `A4Z_SECRET_` — values are masked (`***`) in logs;
- **OS keyring** via [`a4z secrets`](cli-reference#a4z-secrets) (`set` / `list` / `delete`) — referenced as `${secret:NAME}` in profiles.

```bash
export A4Z_SECRET_API_TOKEN="ghp_xxxxx"
a4z run deploy.yml
```

In the workflow:

```yaml
- id: call-api
  uses: http
  with:
    url: https://api.example.com/deploy
    headers:
      Authorization: Bearer ${{ env.A4Z_SECRET_API_TOKEN }}
```

## Run history (SQLite)

`a4z` journals every execution to a local **SQLite** database:

```
<Git repository root>/.automate4z/runs.db
```

- **One predictable location per repository**: the database is anchored at the enclosing Git repository's root (outside a Git repo: the workflow's directory). The CLI and the Studio share the same history.
- **Content**: runs (status, resolved inputs, durations, exit code), their steps (statuses, RCs, skip reasons), their named outputs and their log lines. **Secret values are masked before writing** — never stored in clear.
- **No external service**: pure-Go SQLite driver (no cgo), the database is a plain single-user local file.
- **Rotation**: `--keep-runs` (default 50) bounds the retained history.

Querying the history — three entry points:

```bash
a4z runs list                       # runs, most recent first
a4z runs show 01HZ4K3Q2R…          # one run's detail: steps, RCs, durations
a4z run wf.yml --resume 01HZ4K…    # resume, skipping already-succeeded steps
```

…or the **History** tab of the [Studio](studio/overview), which reads the same database.

The **files** your tasks produce (NDJSON reports, listings, `junit.xml`…) remain ordinary files at the paths your workflows choose — the database only stores the journal. Internal execution artifacts (plugin outputs, notably) go under `.automate4z/runs/<run-id>/<step-id>/`.

:::tip
Add `.automate4z/` to your `.gitignore`: the run history is local state, not code.
:::

## Exploring from the terminal

The binary ships its own documentation — no need to leave the terminal:

```bash
a4z schema --list-tasks       # the 30 tasks, with category and summary
a4z docs data-compare         # a task's documentation (inputs, outputs, examples)
a4z schema --task zos-jobs    # a task's input JSON Schema
a4z runs list                 # the workspace's run history
```

## The web interface (Studio)

Everything the CLI does can also be done in the browser:

```bash
a4z serve                     # opens the Studio on http://127.0.0.1:4500
```

The Studio edits workflows (forms or YAML), runs them, shows history and results — see the [Studio section](studio/overview). To hand a workflow to a non-developer operator, **App mode** (`a4z run <wf> --ui`) opens a locked surface limited to the inputs declared in the workflow's `ui:` block.

## Exit codes

| Code | Meaning |
|------|---------|
| `0` | Success |
| `1` | Business failure (lint with errors, run with a failed step) |
| `2` | Internal error (file not found, invalid YAML, unexpected error) |

## Complete example — Local CI pipeline

```yaml
apiVersion: automate4z/v1
kind: Workflow
name: ci-local
description: Local CI pipeline — lint, build, tests, notification.

inputs:
  repo:
    type: string
    default: .
  notify:
    type: boolean
    default: false

steps:
  - id: vet
    uses: shell
    with:
      run: go vet ./...
      workdir: ${{ inputs.repo }}

  - id: lint
    uses: shell
    with:
      run: golangci-lint run ./...
      workdir: ${{ inputs.repo }}
      timeout: 3m

  - id: build
    needs: [vet, lint]
    run: go build -o ./bin/app ./cmd/app
    timeout: 5m

  - id: test
    needs: [vet, lint]
    uses: shell
    with:
      run: go test -race -count=1 ./...
      workdir: ${{ inputs.repo }}
      timeout: 10m

  - id: notify-ok
    needs: [build, test]
    if: ${{ success() && inputs.notify == true }}
    uses: http
    with:
      method: POST
      url: https://hooks.example.com/ci
      body:
        status: success
        workflow: ${{ workflow.name }}
        runId: ${{ workflow.runId }}

  - id: notify-fail
    needs: [build, test]
    if: ${{ failure() && inputs.notify == true }}
    uses: http
    with:
      method: POST
      url: https://hooks.example.com/ci
      body:
        status: failure
        workflow: ${{ workflow.name }}
```

```bash
a4z lint ci-local.yml
a4z plan ci-local.yml --input notify=true
a4z run  ci-local.yml --input notify=true --parallelism 2
```
