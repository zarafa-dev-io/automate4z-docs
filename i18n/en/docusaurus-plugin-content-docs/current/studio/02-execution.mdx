# Run a workflow

Running a workflow is **not** done from a dedicated panel in the editor. It is driven
from the **workflow header** (the **Overview / Topology / Executions / Editor** tab
bar), which stays visible and actionable **whatever tab is open**. It hosts the **Run**
button, the **Stop** button while a run is in progress, and a **status badge**.

Runs execute **in-process** (no `a4z` subprocess) and are recorded with
`trigger = studio`.

| Badge | Meaning |
| --- | --- |
| **Running…** | The run is in progress. |
| **✓ Succeeded** | The run completed successfully. |
| **✕ Failed** | The run failed. |
| **⊘ Cancelled** | The run was cancelled (via **Stop**). |

## Launch & stop

The **Run** button is **disabled while the workflow schema is invalid**; the tooltip
then reads *"Fix the errors before running"*. Fix the reported errors in the
[editor](./editeur) (or [no-code](./no-code) mode) to re-enable it.

Clicking **Run** **automatically switches to the Executions tab** and starts the run —
**unless** inputs or credentials are required: a **form** then takes over before any
launch (see below).

While a run is in progress, the **Stop** button asks for a **"Force stop?"**
confirmation before interrupting the run (`POST /api/runs/{id}/cancel`). The badge then
switches to **⊘ Cancelled**.

:::info Where to click
**Run** and **Stop** live in the **workflow header**, not in the editor. You can launch
and monitor a run while staying on the **Editor**, **Topology** or **Overview** tab.
:::

## Refusals & pre-launch forms

On start (`POST /api/runs`), the server **validates and completes** the request
**before** launching the engine. Depending on the case:

| Situation | Behavior |
| --- | --- |
| **Invalid workflow** | Run **refused**; diagnostics are returned. |
| **Missing required inputs** | An **inputs form** appears (`enum` → **select**, otherwise **text** field). |
| **Undefined `${secret:NAME}`** | Run **refused**: define the secret first (see [Secrets](./secrets)). |
| **Missing z/OS credentials** | A **user / password form** is presented. |

**z/OS credentials** are requested **only if the profile does not already provide
them**. They are **used once** for that run and **never stored**. In the logs,
**passwords are masked**; **usernames** stay visible.

## Live monitoring

Once launched, the run is monitored in the **Executions** tab. The engine's **NDJSON**
event stream is delivered over the `/ws/runs/{id}` WebSocket and feeds, in real time:

- **scrolling logs**;
- a **Timeline (Gantt)** whose **"now"** marker advances as the run proceeds;
- the **DAG view** in the **Topology** tab, which reflects each **node's live status**
  (running / succeeded / failed / cancelled / skipped).

When the run finishes, history reloads and the completed run is **auto-selected**.
History retention applies after each run (see [Settings](./settings)).

## Results & artifacts

When the run finishes, the **per-task outputs** and the **Artifacts** section appear in
the run detail. **Artifacts** are files detected in the workspace (e.g. an archive) and
are offered with **download links**.

These remain viewable **even for a failed run**: partial outputs produced before the
failure are kept.
