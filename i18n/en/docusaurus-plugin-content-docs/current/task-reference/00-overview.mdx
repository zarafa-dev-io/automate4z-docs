# Built-in tasks

automate4z ships **39 built-in tasks** in the `a4z` binary. They compose freely within a single workflow — that is the product's philosophy: each task does one thing, and the rich scenarios (testing a batch, impact-driven builds) are documented **compositions**, not black boxes.

## Cross-cutting conventions

### Implicit outputs

Every step automatically exposes these three outputs, whatever the task:

| Output | Type | Description |
|--------|------|-------------|
| `exitCode` | integer | Return code (0 = success) |
| `duration` | string | Execution time (Go format, e.g. `1.23s`) |
| `status` | string | `success`, `failure`, `skipped` or `cancelled` |

### Relative paths

Relative paths are resolved against the **workflow YAML file's directory**, not the `a4z` process CWD.

### z/OS profiles

The `zos-*` and `z-deps` tasks resolve their credentials via the profile given by `--profile <name>` at launch, or the `default` profile (`~/.automate4z/profiles/<name>.yml` + native keyring for secrets).

### Encodings

Transfers between the local workstation (UTF-8) and z/OS (EBCDIC) are handled by the adapters with a sane default and an explicit `encoding` option. The data tasks (`data-inspect`, `data-compare`, `testdata-generate`…) share the same embedded EBCDIC tables: `ibm-1047`, `cp037`, `cp1140`, `cp297`, `cp1147`, `cp500`, `cp1148`.

### Gates and verdicts

Many recent tasks (`assert`, `data-compare`, `job-assert`, `build-impact`, `zos-build`…) distinguish **"the check failed"** (the result is there, and it is bad) from **"the check could not run"** (technical breakage). That contract — and the `continueOnError` + `if:` idiom that goes with it — is explained once and for all in [Gates, verdicts and tests](../workflow-spec/gates-et-tests).
